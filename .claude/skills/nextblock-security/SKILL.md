# NextBlock security gate

Every item below is a real hole that shipped at least once (2026-10-17 → 11-03). The automated
gates catch most of them; the checklist covers what they cannot see. A change is not done until
the gates pass and every checklist line that applies has been answered.

## 1. Run the gates

```bash
npm run security:check        # service-role boundary, action actors, sandbox guards, HTML sinks, migration lint, posture runner guard, grant-pass lockstep, generated migration copies, Supabase CLI targets (~20 s)
npx vitest run <paths you touched>
```

For a migration, a policy, a grant, or anything in `GRANTS_SQL`, also:

```bash
npm run db:migrate:check      # read-only; the new file must be listed as pending
# replay every migration into a disposable local database, then the posture gate:
SUPABASE_PROJECT_ID=nextblock-ci npx supabase start --workdir libs/db/src -x realtime,storage-api,imgproxy,kong,mailpit,postgrest,postgres-meta,studio,edge-runtime,logflare,vector,supavisor
npm run security:db-posture -- --db-url postgresql://postgres:postgres@127.0.0.1:54322/postgres
npx supabase stop --workdir libs/db/src --no-backup
```

`security:db-posture` runs the post-apply grant pass first (every deploy does) and fails on any
FAIL or skipped assertion; it refuses non-local hosts. Never run it, or `security-verify.sql`,
against production. CI (`.github/workflows/security.yml`) runs all of this on every push and PR,
but run it before handing work back: CI only reports after the push.

A Stop hook (`.claude/settings.json` → `tools/scripts/claude-security-stop-hook.mjs`) runs
`security:check` whenever a turn ends with code changes and sends you back if it fails. Fix the
cause; never weaken a check, add an allowlist entry or a grandfather entry to make it pass
without saying so to the user.

## 2. Checklist

**Server actions and routes**
- Every exported function of a `'use server'` file is a public POST endpoint, reachable from any
  route (`proxy.ts` only gates `/cms` URLs). It authenticates and authorizes itself BEFORE any
  read: `requireCmsAdmin()` / `requireCmsStaff()` (`lib/auth/cms-actor.ts`), `requireEcomAdmin()` /
  `requireEcomStaff()` (`libs/ecommerce/.../require-ecom-role.ts`), Cortex `requireActorRole`.
- Never trust an id, price, role, owner or token from the client. Re-derive ownership on the
  server (order access tokens: `order-access-token.ts`; UCP carts: `access_token_hash`).
- A payment provider's browser callback is attacker-controlled. Verify every id it names with the
  provider's API before storing it, and never let it set a product, plan or paid state
  (`evaluateFreemiusCheckoutLicense`: a guest could attach any license to their order and read its
  key). A page that reveals a secret (license key) re-checks that it belongs to the order.
- A helper that returns the service-role client enforces the enrolled second factor, not just the
  role: server actions never pass the CMS layout's 2FA redirect. Use `getCmsActor()`; the
  ecommerce lib uses the gate the app registers (`lib/auth/second-factor-gate.ts`). A `'use server'`
  module never builds its own service-role client after a cookie-client role read: it takes the
  client `requireCmsAdmin()` returns (the package actions did not until 2026-11-13). A role read
  followed by `getServiceRoleSupabaseClient()` is the same first-factor check: resolve the actor
  with a helper first, also for a public action's staff branch (the checkout success page). Gates:
  `server-action-actors.test.ts`, which since 2026-11-13 scans every `'use server'` module of the
  app and the libraries for a client built from the secret key (exceptions in
  `OWN_SERVICE_CLIENT_ALLOWED`, each with why), and every server action under `app/cms` and
  `app/actions` for a role read that can reach the service role with no second-factor helper
  (`findRoleReadsBeforeServiceRole`, exceptions in `ROLE_READ_BEFORE_SERVICE_ROLE_ALLOWED`). That
  second check only sees that a helper is reached, and only in those trees: check the order of the
  calls, and actions elsewhere, by hand.
- A server action that can reach a Freemius coupon push (`syncCouponToFreemius`,
  `syncProductSaleCouponToFreemius`, `deleteCouponFromFreemius`: signed with the developer key pair,
  and a coupon with no product scope applies to every product) awaits `requireEcomAdmin()` /
  `requireCmsAdmin()` before every call toward the push, as a whole statement, an initializer or a
  plain `=` assignment: never `.catch()` / `.then()` on it, `void`, or a check on one branch only.
  Reword a refusal with `let admin; try { admin = await requireCmsAdmin(); } catch { throw … }`.
  Call pushes directly (method calls, `.call` / `.bind` and aliases are not followed) and list a
  new push in `FREEMIUS_COUPON_PUSHES`. Gate: `server-action-actors.test.ts` (the full rule: docs/04
  → "A Freemius coupon push needs a verified admin").
- Partner portal (Affiliates): every page, action and route calls `requireRetailerPage()` /
  `requireRetailer()` (`lib/affiliates/retailer-actor.ts`) first: session, enrolled second
  factor, role `RTL` from the caller's own `profiles` row (`String(role)`), the program active
  (`isAffiliatesProgramActive()`: Affiliates and the Commerce Pro it requires, failing closed;
  never `verifyPackageOnline('affiliates')` alone, which `package-state.test.ts` refuses), not
  suspended. The actor's affiliate is the only one it may touch; filter every write on its id
  and user id.
- An approval publishes exactly what the reviewer saw: pin every field it copies, not only the
  one an edit bumps (storefront Approve checks `draft_version` and a fingerprint of the profile
  snapshot, `fingerprintAffiliatePublishedProfile`). A per-page action that mails admins has a
  rate limit inside its conditional UPDATE (the resubmission cooldown).
- A route handler that mutates with cookies needs the same checks. A staff route handler never
  passes the CMS layout's 2FA redirect either: it opens with `const actor = await getCmsActor()`
  and refuses a missing actor (403 "Complete two-factor verification, then try again." for a
  signed-in user whose factor is pending, 401 without a session) and a role outside its rule,
  before it reads the body or touches storage or the database, the Cortex AI request quota or a
  model (until 2026-11-14 the five staff upload routes, the product picker, the update check and
  the four staff AI routes read the role through the cookie client). Gates, all in
  `server-action-actors.test.ts`: `analyzeStaffRouteGates` checks that order from the code's
  structure for `STAFF_UPLOAD_ROUTES` and `STAFF_ROUTES` (a route under
  `app/api/{media,upload,process-image}`, `app/api/ai` or `app/api/cms` that neither list names
  fails unless reviewed), and `findRouteRoleReadsBeforeServiceRole` fails any route handler of the
  app that can reach a role read and the service role with no second-factor helper (reviewed
  exceptions in `ROUTE_ROLE_READ_BEFORE_SERVICE_ROLE_ALLOWED`, each with why). Cron routes check
  their secret with `isCronRequestAuthorized()` (`lib/cron/cron-secret.ts`: SHA-256 of both sides +
  `timingSafeEqual`; never compare the header with `===` / `!==`) and fail closed without it; the
  FX sync (`/api/cron/sync-currencies`) is the one documented route that stays open while
  `CRON_SECRET` is unset, and the payout route (`/api/affiliates/cron/payouts`) also refuses a
  secret under 16 characters.
- A public route whose request spends a shared vendor credential (the Freemius developer key pair)
  is limited per client network and per instance, counted after its capability check and only for
  work that runs. An order access token limits nothing by itself: `POST /api/checkout` mints one
  for anyone. Read the address as `resolveAffiliateSignupClientIp` does (`x-vercel-forwarded-for`
  only when `VERCEL=1`) and bucket it with `maskAffiliateVisitorIp` (the checkout sync,
  `app/api/checkout/freemius/sync/route.ts`; the vendor claim and trial routes through
  `app/api/packages/vendor-route-limits.ts`, the claim also remembering an answered miss for 60 s).
  A read that page visits drive is cached, shared
  while in flight and capped per instance (the order license, `getFreemiusOrderLicense`).
- A public action that asks a provider about an id the caller supplies checks the id's shape and
  finds it on one of the store's own rows first, so made-up ids never spend the operator's API rate
  limit: the checkout success page asks Stripe only about a `cs_test_` / `cs_live_` id that an
  order stores in `stripe_session_id` (until 2026-11-13 any `cs_` string cost a Stripe call). That
  makes the session-id write load-bearing: checkout hands out a session's URL only once its order
  stores the id, and on a failed write expires the session and answers the keyed 503
  (`providers/stripe.test.ts`, `stripe/checkout.test.ts`); never answer a stranded buyer by sending
  unknown ids to Stripe again.

**Service-role client** (bypasses every RLS policy)
- A module that builds, hands out or keys it imports `'server-only'`; the key is read only by
  `lib/setup/service-key.ts`; import types from server modules with `import type`; no secret
  behind `NEXT_PUBLIC_` or `next.config.js` `env`. Gate: `service-role-boundary.test.ts`.
- Under the service role RLS is not a boundary: the in-code role check IS the authorization.

**Stored secrets** (`libs/db/src/lib/secret-crypto.ts`)
- Seal and open every stored secret for its slot, the row and field it lives in:
  `encryptWithEnvKey(value, siteSettingSecretSlot(key, field))`, `tryDecryptWithEnvKey(envelope,
  sameSlot)`. Never one decrypt helper for several rows (Cortex opened its three keys with the
  OpenRouter one): an envelope copied into another row must read as missing there, above all where
  the plaintext leaves the server (SMTP AUTH to a saved host, a form that shows it).
- A new secret row is named `<feature>_secret` or `<feature>_api_key`: 02038's pattern then keeps
  it service-role only with no migration. Its screen re-seals version 1 envelopes on save
  (`resealWithEnvKey`). Gates: posture §42, `secret-crypto.test.ts`.
- The Freemius developer key pair (`payment_secret.freemiusDeveloperSecretKey`,
  `FREEMIUS_DEVELOPER_*`, or the legacy names once Freemius accepts them) is a master key for the
  whole Freemius account: every product's secret, licenses and their keys, owners' emails,
  coupons, trials. Never keep it under the legacy one-product names (`FREEMIUS_PUBLIC_KEY` /
  `FREEMIUS_SECRET_KEY`, the CMS one-product fields), which also open checkouts and verify
  webhooks: the key policy refuses a pair there that it knows (working, sharing a key with a
  dedicated pair, or accepted by Freemius earlier in the instance's life), and the one gap is an
  instance that has not yet seen Freemius accept that pair: one started after a revocation, or one
  whose developer checks Freemius has not answered yet (a cold start during a throttle or an
  outage). Move the pair out of the one-product names (the 0.23.4 upgrade notes say how), and
  after you rotate the developer pair, delete the old one from every field, the one-product names
  included: CMS → Payments has a remove box under each stored secret (`savePaymentCredentials`
  `remove`, behind `requireEcomAdmin()`, refused on the sandbox), and a removed or cleared CMS
  field gives its `FREEMIUS_*` name back to the deployment's value at each instance's next
  hydration, so clear the env names too.
  Only `libs/ecommerce/src/lib/freemius-developer-api.ts` signs with it: work goes through
  `freemiusDeveloperRequest` / `withFreemiusDeveloperScope`, every id through `toFreemiusId`
  (digits only; a webhook's `plugin_id` only chooses among the account's own products), no
  developer-scope response is logged (plugins carry each product's keys), the pair never enters
  `process.env`, and on the sandbox only `openFreemiusCatalogReader` (GET, catalog paths) runs, for
  the reset alone: the CMS Sync from Freemius refuses there, `findDeveloperKeyProblems` checks every
  caller of the reader, and every other entry, `describeFreemiusDeveloperPairs` and
  `confirmFreemiusOneProductKeys` included, refuses before it resolves or sends a key (each pinned
  in `SANDBOX_GUARDS`). Which configured keys a product may use is decided only in
  `freemius-key-policy.ts`, never by a new fallback: `freemiusKeysMayBeDeveloperPair` for the keys
  `FREEMIUS_PRODUCT_ID` binds (configuration and memory only, failing closed),
  `decideFreemiusOneProductStandIn` for the one-product keys standing in. Where it needs Freemius to
  confirm those keys are a product's own (`confirmFreemiusOneProductKeys`: one product-scope GET,
  the only request signed with them), an instance asks at most 10 times a minute and keeps bounded
  memory, and a webhook asks only once its signature matches that secret. A webhook verifies with
  its own product's secret only: the route awaits `getFreemiusWebhookVerification` (503 on
  `unverifiable`) and passes the verified `productId` to every handler, the refund and dispute
  handlers included (the old `verifyFreemiusWebhookSignature` stays synchronous: an async one would
  let `if (!verify…)` pass every forgery). Freemius failing to answer is never "not owned" (a
  missing id from an unanswered re-list throws `unavailable`, and a 2xx that is not the product
  list, product or catalog page asked for is no answer: a product read keeps its last keys and Sync
  stops; only a 2xx that IS the product, with no `error` member, confirms the one-product keys), a
  first-page 404 of the probe refuses a pair with no working verdict and a working
  one only at a second 404 30 s later, last-good product secrets verify for 70 minutes at most, and
  forged webhooks reach Freemius at most once a window and the logs at most once per product and
  per reason a minute (both bounded: `createFreemiusLogThrottle`). Readiness never waits on
  Freemius, so a surface acting on it (the CMS Payments toggle) awaits the blocking
  `getFreemiusDeveloperStatus()` first. Gates: `freemius-developer-api.test.ts`,
  `freemius-developer-flows.test.ts`, `freemius-key-policy.test.ts`,
  `freemius-keys-end-to-end.test.ts`, `providers/freemius.test.ts`, `sandbox-guards.test.ts`.

**RLS policies**
- Every policy names its roles (`TO authenticated` …); one without `TO` also applies to `anon`.
- No `USING (true)` / `WITH CHECK (true)` for `anon`/`authenticated` on a table holding users,
  orders, coupons, licenses, tokens, revisions, settings, 2FA, carts or messages.
- An authorization column (`profiles.role`) is pinned by column grants first (02025), then
  `WITH CHECK` and a trigger. A self-service `FOR UPDATE` policy covers every granted column.
- ADMIN branches on orders, profiles (other rows), the site_settings ADMIN tier and the commerce
  tables use `is_admin_mfa()` (aal2 when a factor is enrolled, 02023); CMS screens read those
  rows with the service role after the in-code check, never through the cookie client. The
  site_settings secret rows answer to no API session at all (02038): `is_admin_mfa()` also passes
  an admin who enrolled no factor, so it is no boundary for a secret. Neither does a row that
  decides authorization or the first-boot gate: `is_admin_created` is written by no API role
  (02041, RESTRICTIVE policies), because on the sandbox every visitor is that admin.
- Draft/scheduled/archived rows and their children (media, stock, categories) stay staff-only.
- Roles in SQL are compared as text (`(SELECT public.get_current_user_role())::text = 'RTL'`,
  `role::text = 'RTL'`): the sandbox replays every migration in one transaction, where 02029's
  label is not committed. `findEnumRtlLiterals` refuses an `'RTL'::public.user_role` cast outside
  a plpgsql body.

**Grants** (decide whether a role may touch a table at all; RLS decides which rows)
- New table: `ENABLE ROW LEVEL SECURITY`, `GRANT SELECT … TO anon` only if publicly readable,
  writes to `authenticated, service_role` only. `anon` holds no write grant anywhere (02025).
- Any revoke from `anon`/`authenticated` that the blanket grants of `GRANTS_SQL` hand back goes
  into `API_ROLE_REVOKE_SQL` in BOTH `apps/nextblock/tools/lib/migrate-core.mjs` and
  `apps/nextblock/lib/setup/schema-apply.ts`, or the next deploy undoes it (02013 → 02024,
  02022 → 02025). Gates: `migration-grants.test.ts`, `migrate-core.test.mjs`, the posture job.

**Functions**
- No `SECURITY DEFINER` function in `public`: put it in `private` with a `SECURITY INVOKER`
  wrapper (02021). Any definer function sets `search_path`, and the file revokes EXECUTE from
  `PUBLIC, anon, authenticated` (Postgres grants PUBLIC on create; Supabase grants anon and
  authenticated by name). Service-role-only RPCs go into `API_ROLE_REVOKE_SQL` too.
- Atomic counters and limits (coupon redemptions, 2FA attempts) are one `UPDATE … RETURNING`.
- Extensions go in `extensions`, never `public` (advisor 0014).
- A function a later migration changes keeps its return type and parameters, or that migration
  drops it first and the earlier file creates its final shape: `private` survives the sandbox
  reset's DROP SCHEMA public (`migration-replay.db.test.ts`). After editing a migration, regenerate
  its copies (`generate:migrations-bundle`, `generate:sandbox`): `generated-migration-copies.test.ts`
  (in `security:check`) fails until then.
- A function never casts text a writer controls with a bare `::numeric` or `::integer`: numeric
  takes 'NaN' (it sorts above every number, so LEAST/GREATEST clamps it to the maximum) and
  'Infinity', and since PostgreSQL 16 both take '0x10' and '1_000'. Match the text first (02044's
  `v_quantity_pattern`, held to the app's pattern by `stock-quantity-pattern.test.ts`).
- Two writers that lock rows of the same tables take them in one order. Every writer of
  `inventory_items` takes its rows in SKU order (`ORDER BY sku`, the column's collation: never a
  JavaScript sort) in ONE statement, before it writes any variant or product row (the inventory
  trigger writes those at the end of that statement, product totals locked in id order): a sale
  (`apply_order_inventory_deduction` and the app's SQL fallback read the lines once, take every row,
  then deduct), the product publish (before the products row, the rows of every SKU of every product
  whose rows it can write, creating a sellable SKU's missing row there), and every other writer
  through `upsert_inventory_items` / `update_inventory_quantities` / `delete_inventory_items` (02046:
  `upsertInventoryRows`, Cortex's `execute_database_mutation`). A multi-row PostgREST write of
  `inventory_items` takes its rows in the order given and deadlocks with a publish; a row-by-row
  writer that holds a product row while it waits for an inventory row deadlocks with a sale
  (`product-draft-publish.db.test.ts`; docs/09 → "Stock: only what the editor changed", Locks).
- A trigger that recomputes per row what a statement changes costs the square of the rows a
  statement writes (02044's inventory trigger took a 500-SKU publish past the Data API's 8 s
  timeout): sync once per statement from the transition tables (02046), and keep a timed case under
  `statement_timeout = '8s'` in the DB tests.

**Inputs that reach the network, the filesystem or the page**
- Server-side fetch of a user-supplied URL calls `guardedFetch` (`libs/cortex/src/lib/fetch-host-guard.ts`:
  private ranges, every redirect hop, pinned DNS, streamed byte cap); never `fetch()` with
  `redirect: 'follow'`, never report a refused hop's status. Uploads go through `lib/storage/upload-policy.ts`;
  every key a client hands back to a route that reads, writes or records it goes through
  `isAcceptableClientObjectKey`, used or not (`/api/media/record`'s `r2OriginalKey` included), with
  `requireAllowedExtension` wherever the route records the key or names other objects after it
  (`/api/process-image`'s variants). A media row inserted through RLS (the `recordMediaUpload`
  server action, or the Data API) can still name any key, so code that acts on a stored key judges
  it itself (`media-object-keys.ts`).
- A presigned upload URL is a bearer token for its key until it expires. Sign it only with
  `presignBoundPut()` (`lib/storage/presigned-put.ts`): it requires the declared size within the
  kind's limit and binds `Content-Length` and `Content-Type`, so storage refuses any other size or
  type. Return its `headers`, and have the browser send exactly those (`presignedPutFetchHeaders`).
  Supabase signed upload URLs bind neither; the bucket's `file_size_limit` / `allowed_mime_types`
  are the cap there (docs/04 → "Upload URLs").
- Author CSS in a `<style>` element goes through `escapeStyleElementText` (`lib/themes/style-element-text.ts`).
- A `'use server'` export never takes the actor (`actorUserId`, `authorId`, `userId`) or a
  database client as an argument; actor-taking variants live in server-only modules called by
  routes after they authenticate. Gate: `server-action-actors.test.ts`.
- Authored HTML renders through `sanitizeAuthoredBlockHtml` (`@nextblock-cms/utils`, an allowlist
  on sanitize-html; `sanitizeAuthoredSvgMarkup` for an `<svg>`'s inner markup; the app's
  `lib/blocks/inlineScriptNonce.ts` re-exports it) wherever it is written into a page: React
  `dangerouslySetInnerHTML`, html-react-parser, `innerHTML`, a `text/html` Blob. This covers a CMS
  preview too, and lib components sanitize inside themselves (the app wrappers never see the
  value). The CSP is only a backstop. Since 2026-11-04 `script-src` carries `'strict-dynamic'`, so
  a `<script src>` in the markup no longer runs from an allowed host without the nonce. But a script
  that a trusted script inserts still runs from any host (React 19 inserts every
  `<script async src>` it renders on the client), and a meta refresh needs no script. Gate:
  `html-sinks.test.ts` (every sink listed in `HTML_SINKS` with why it is safe; a sanitized sink
  must still call the sanitizer; a component marked `noCallers` may not be imported or used). A text
  block holding Tiptap JSON (`isTiptapJsonString`) skips the sanitizer in its callers and renders
  through React; never put that exemption inside the sanitizer, because raw sinks inject
  JSON-parseable strings as HTML. Redirect targets go through `lib/auth-redirects.ts`.
- The CSP is built in `proxy.ts` (`createContentSecurityPolicy`, docs/04).
  - Any script written into the page carries the layout's nonce (`x-nonce`).
  - Pages stay dynamically rendered: a prerendered page has no nonce, so `'strict-dynamic'` blocks
    every script on it.
  - Never drop `'strict-dynamic'`, `script-src-attr 'none'`, `object-src 'none'` or
    `base-uri 'self'`.
  - Never add `'unsafe-inline'`, `'unsafe-eval'`, `*` or a scheme such as `https:` or `data:` to
    the production `script-src` (`blob:` is the one scheme it keeps).
  - Keep the fallback host list to hosts the app actually loads from. Browsers without
    `'strict-dynamic'` still trust every host on it, gtm.js and www.google.com's JSONP included,
    so the sanitizer is their only guard.
  - Gate: `proxy.test.ts` ("Content-Security-Policy") pins both `script-src` lists.
- Partner storefront JSON (`affiliate_pages.draft_content`, which a partner can PATCH over the
  Data API, `published_content`, copilot sections) is untrusted wherever it is read: run
  `sanitizeStorefrontDoc` at read time with `getStorefrontImageOrigins()` (server-side, passed
  down as a prop), render only through `StorefrontRenderer`, and edit only with
  `@nextblock-cms/affiliates/editor`. Never load partner JSON into `NotionEditor` (its kit keeps
  arbitrary HTML) and never render it as HTML.
- Partner uploads go through `/api/affiliates/upload` only: `requireRetailer()`, same-origin,
  refused while the page is in review, byte-capped before buffering, magic-byte sniffed (SVG
  never reaches sharp), decoded under a pixel cap (12 MP for AVIF, which costs about 25 bytes a
  pixel; 50 MP otherwise), one decode at a time per process with a 30 s timeout, re-encoded to a
  metadata-free JPEG, keys built on the server under `affiliates/{avatars|pages}/<affiliateId>/`.
  An upload never deletes the avatar the approved snapshot shows. No staff path touches the
  partner namespaces `affiliates/avatars/` and `affiliates/pages/` (`PARTNER_UPLOAD_NAMESPACES` /
  `isPartnerUploadKey` in `lib/storage/upload-policy.ts`, which counts a key wherever storage could
  put it: a `?` or `#` in the key or after any decoding round counts outright, since it does not
  model where the URL path ends; escapes decoded until none is left, 4 rounds at most; tabs and
  newlines dropped, backslashes read as slashes, case ignored; the path as written and with its
  dot segments resolved; and the raw key also read in the URL parser's order (empty segments kept,
  dot segments, `%2e` spellings included, resolved before anything is decoded, so an escaped `/`
  never splits a segment), then decoded, and that reading again on the key as storage-js
  `upload()`, `update()` and `uploadToSignedUrl()` send it (repeated slashes collapsed first); a
  malformed or still-encoded escape, or a `..` that leaves the bucket, counts). Never hand storage
  a client's key on its spelling alone: on the native Supabase backend storage-js puts the key
  into the request URL (raw, or for `upload()`/`update()`/`uploadToSignedUrl()` with repeated
  slashes collapsed), where the URL parser resolves `..` / `%2e%2e` and ends the path at `?` or `#`
  (before it resolves the dot segments after it), and the storage server decodes `%xx`.
  Each path, with the test that holds it:
  - a folder the client names: `resolveUploadFolder` refuses one inside a namespace
    (`/api/upload/proxy`, `/api/upload/presigned-url`: `upload-policy.test.ts`,
    `upload/proxy/route.test.ts`, `upload/presigned-url/route.test.ts`), and so does
    `/api/media/r2-presigned` through the server entry's `validateR2PresignedUploadPayload`; its
    signer `createR2PresignedUpload` (`lib/custom-block-r2-upload.ts`) refuses such a key for a
    payload nobody validated, encoded and `%2e%2e` spellings included
    (`custom-block-r2-upload.test.ts`), any key holding a `?` or `#`, and the spellings only the URL
    parser's order puts in a namespace (`affiliates//../pages/…`, `x%2fy/../affiliates/pages/…`;
    until 2026-11-14 it signed those and `./affiliates/pages/<id>/x.jpg?/../../../../…`:
    `partner-upload-namespaces.test.ts`). Every builder strips `%`, `?` and `#`, so an encoded
    folder becomes a literal folder outside the namespaces;
  - a key the client hands back: `/api/process-image` and `/api/media/record` judge every key in
    the request with `isAcceptableClientObjectKey` and `requireAllowedExtension` (`isSafeObjectKey`,
    only the characters the builders mint, so no `%`, `?`, `#` or whitespace, an allowed media
    extension in the last segment, no partner key) before any storage call or insert
    (`process-image/route.test.ts`, `media/record/route.test.ts`; a percent-encoded partner key
